# SAAMAN 1.0.20 trajectory and validation

The production STAR/vector predictor now integrates speed, altitude, distance and time instead of assigning altitude linearly across a path and taking the maximum of separate horizontal/descent times. The editable implementation is ui/src/maestro-trajectory.ts; tests include energy accounting, convergence, endpoint conditions, telemetry recording and replay.

## Scope and assumptions

This is an **energy-accounted kinematic model**, not a complete BADA or OpenAP mass/thrust/drag solver. It uses the selected aircraft profile's nominal vertical rates, limited by supervisory rate caps. With a constant-CAS nominal rate, the specific-energy budget accounts for density-related TAS changes. A commanded CAS change consumes or releases energy: acceleration reduces climb/increases sink; deceleration reduces available sink. Descent is not converted into an uncommanded climb. The nominal energy budget is not an inferred exact aircraft thrust setting.

The integration step is five seconds, with a 15-second initial response and a 0.5 kt/s CAS change assumption. These values are local planning choices. There is no mass estimate, flap/gear model, upper-air wind profile or calibrated acceleration model in this release. Generic/proxy performance is labelled; gain is withheld where existing eligibility rules or downstream feasibility fail. Feasibility means meeting the configured model endpoint, not certified aircraft reachability.

Pre-feeder prediction carries present altitude and speed through forecast climb/descent and uses known cleared/final climb levels and assigned IAS/Mach. Future descent release remains assumed. Current lower cleared levels bound the pre-feeder descent plan; future level/clearance sequences remain unknown. IAS/CAS terminology follows the existing ISA conversion; measured IAS and temperature are unavailable. Surface wind is used only in the lowest 3,000 ft rather than throughout the entire high-altitude arrival. A three-degree path and 150 ft pressure-altitude threshold are local approximations.

After the feeder, the selected workbook distance remains the baseline. Direct-to information, route geometry and existing vector/final detection modify the path. If speed/height cannot meet the configured endpoint, a non-final planning path is lengthened and the required extra track is explicitly reported as unconfirmed future vectors. An observed final is never lengthened to disguise invalid simulator height/speed; it is flagged in Errors and supervision. This release does not make unknown future vectoring intentions observable.

## Sequencing and instructions

Known sequence stability, manual slots, closures and Frozen protections remain. A flight already across a feeder stays ahead of its upstream follower when constructing an initial sequence. A route whose first point is the feeder no longer falsely marks an upstream aircraft passed. Automatic post-feeder Superstable scheduling uses current rates; legacy EuroScope-route/manual/Frozen policies keep their existing protections. Explicit live Superstable targets retain the slot while remaining work follows the filtered trajectory reference. Requested gains exceeding the current conservative capability estimate are withheld and identified in supervision.

The earlier delay could be retained as a baseline and also counted in spacing components during promotion to Frozen. Automatic baseline work now excludes those dynamic components, and live Frozen instructions use the current filtered prediction against the protected target. No automatic TMA/Frozen gain is invented to recover a missed target. Guidance reports the point, prediction, reference, target, applicable constraints, current earliest planning estimate and expiry. Constraint descriptions are causal labels, not an additive delay budget.

The 30-second ETA deadband / 15-second persistence from 1.0.19 remain planning heuristics. Initial adoption of the new trajectory model rebases its automatic reference without removing manual edits or resetting established aircraft states. Shared schema saaman-1.0.20 requires a new channel and matching clients.

## Session recording and replay

In the separate supervisory panel: Start session recording, run the exercise, Stop recording, Export recording. It is opt-in and memory-only until exported. Export before closing the window. The cap is 64 MiB of estimated stored text or 3,600 frames; a changed source stops recording. Settings/edits and route geometry are dictionary-compressed; route times, positions and clearances remain per-frame. The starting checkpoint preserves existing history. Same-timestamp controller changes retain a control checkpoint; the replay restores these checkpoints rather than claiming to independently verify the command calculation. Telemetry includes original SDK runway assignments and sector geometry, independently of AMAN overrides; retained Landed display entries are excluded from input, while still-observed aircraft omitted from the display remain captured.

After building dependencies, replay with:

```text
node scripts/replay-recording.mjs ESSA-AMAN-recording.json report.json
```

The tool compares state, order, ETA, STA and instruction against recorded results and reports spacing conflicts. A modified engine can legitimately differ; inspect the report rather than interpreting every difference as a defect. Do not switch rooms/reset the exercise while recording: stop/export and begin another recording. Source changes stop automatically, but a reset with the same callsign/source is not automatically detectable in this format.

## 1.0.22 automatic order reconciliation
Automatic forecast order is distinguished from controller order/target edits. A live model pair with more than 60 seconds of filtered ETA inversion must persist for 45 seconds before swapping. ## 1.0.24 order, time and minimum semantics
FlightEdit.targetKind distinguishes `time` (explicit Stable time selection or requeue time) from `sequence` (chosen relative order). Reorder emits an order without an automatic absolute target for each affected aircraft; deliberate time assignments remain. Future forecast changes therefore recompute work from current independent predictions and actual constraints. The new leader does not inherit the delay of an old slot. A slower aircraft deliberately moved ahead can still require genuine delay for the faster follower, and changing wake order recalculates the actual required gap.

Local transport and shared production migrate unmarked legacy order+target edits only for live-model Superstable/Frozen aircraft without manual timing evidence or closure position. Ambiguous legacy Stable instructions are retained. New explicit time edits carry `targetKind: time` and cannot be misclassified. Targets identified as obsolete are not cleared by modifying the user's saved file directly: the running plugin persists its normalized plan through the usual API.

A newly seen ordinary arrival already past its feeder uses the current time as its insertion floor. Old ordinary-entry floors are released after feeder crossing. A tagged or identifiable legacy missed-approach recovery minimum survives this release, including a subsequent settings change. A deliberate Recompute can clear that minimum. Automatic Frozen timing is independent of a manually held order, and uses current rate/wake/closure rules; a manually assigned absolute time remains authoritative.

The FIN1NX observation contained an order-0 edit with a 15:05:15 UTC target and a 15:01:35 filtered prediction: 220 seconds of unnecessary work with no rate/wake/closure ahead. Tests reproduce that class of obsolete-slot delay and its release; the archived scenario snapshot was empty after the user ended the session, so this is not a claim of replaying that exact live aircraft path.

## 1.1.0 operating policy (supersedes earlier phase/gesture descriptions)

Production configuration and the native saved-config migration fix Stable/Superstable at 15/4 minutes. The frozen default is 3.5 minutes. Explicit gain dragging is allowed in every airborne phase and can enter/leave Frozen; it is bounded by the original allocation. Explicit before/after insertions are separate controller order actions. Unstable allocations follow provisional forecasts, while Stable and Superstable order restrictions follow the confirmed operating specification.

Accepted feeder and runway allocations remain fixed between controller actions, using the accepted transfer interval for feeder spacing rather than automatically replacing it with a changed future-path forecast. Superstable instructions stay fixed until Recompute or Refresh delay. Refresh uses the currently actionable point: feeder before crossing, runway afterwards. Initial/current references are distinct. Missing legacy initial allocations are unavailable.

Maximum-delay limits attempt a feasible insertion respecting physical feeder order and real wake/rate/closure constraints. Unsatisfied limits remain visible as diagnostics rather than capped numbers. Explicit missed-approach before/after insertion does not add the generic ten-minute resume floor. Existing resume/recovery handling remains for a resume without an explicit position.

The Information route uses the independent trajectory samples for remaining point times, normalised to known route geometry. These are nominal path estimates, not EuroScope EET values or knowledge of future controller vectors. Native explicit termination is distinct from controller tracking state and target loss. Known non-terminated FPL metadata is captured separately from radar tracks and deduplicated into inventory tables in recordings.

Coordination lives in the engine-owned operational checkpoint. Concurrent message/acknowledgement changes merge, message content is immutable, and receipts survive handover. It does not change aircraft speed or route assignments. The server continues to relay opaque state.
